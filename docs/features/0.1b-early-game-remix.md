# Early Game Remix — levels 1–30 (Milestone 0.1b)

Status: implemented (pending playtest)
Branch: `feature/0.1b-earlygame-companions`
Decision: `docs/DECISIONS.md` D11

## Goal

The first 30 levels must teach the class and stay fun. Upstream v83 assumes a
large server population and slow progression; for 1–10 friends that turns
levels 1–30 into a slog. This feature makes the early game faster and more
legible **without** touching the client and without changing any mid/late-game
balance.

Design pillars involved (from `GAME_DESIGN.md`):

- **Solo-first co-op** — no content is gated behind "bring N players".
- **Leveling must stay engaging** — quest/PQ/event EXP meaningful, not pure grind.
- **Quality of life over v83 purity.**

## Slice 2 — Ultra Beginner Skills

"Ultra" is **not** a new skill. Cosmic already ships three server-side flags
that massively strengthen the three beginner skills; they were simply off:

| Flag | Effect |
|---|---|
| `USE_ULTRA_THREE_SNAILS` | Shell toss damage is multiplied by player level; consumes one shell per toss (`AbstractDealDamageHandler`) |
| `USE_ULTRA_RECOVERY` | Recovery heal interval 5000 ms → 2000 ms (`Character`) |
| `USE_ULTRA_NIMBLE_FEET` | Massive speed and jump upgrade (`StatEffect`) |

All three are now **on**. They are plain config flags, so this is a data
decision and can be reverted without a code change.

### Consistency defect fixed

`constants/skills/Beginner` declared `THREE_SNAILS = 1001`, identical to
`RECOVERY`. The runtime Ultra-Three-Snails path computes the id dynamically as
`jobType * 10000000 + 1000` (`AbstractDealDamageHandler`), so behaviour was
already correct — this was a consistency defect, not a gameplay bug. It is fixed
to `1000` so the constant matches the WZ and cannot mislead a future reader.
The constant is not referenced by production code, so there is no test for it;
the behavioural guarantee comes from the dynamic id computation.

### Beginner SP bonus

Beginners start without spendable SP, so the three skills stay at level 0
through the slowest part of the game. Beginner jobs (Beginner 0, Noblesse 1000,
Legend 2000) now receive `coop.early_game.beginner_sp_bonus` SP at creation
(default 3). Veteran creators are excluded because they already have a class.

The bonus is applied to the creation **recipe**, because `Character.insertNewChar`
writes `remainingSp` from the recipe; changing the character afterwards would be
overwritten and would need a second DB write.

## Slice 3 — First-job starter kits

Upstream grants one weapon per class inside five NPC scripts
(`scripts/npc/1022000.js`, `1032001.js`, `1012100.js`, `1052001.js`,
`1090000.js`). That scatters balance across JavaScript and duplicates the
Cygnus quest path (`scripts/quest/2010*.js`).

Instead:

- Table `coop_first_job_kits` (migration `coop-1210`, seeds `coop-1211` and
  `coop-1212`).
- One hook at the end of `Character.changeJob`, which is the **single** path
  every advancement uses (NPC scripts, Cygnus quests and the GM command).

`jobid = 0` is the "all classes" bucket and is granted in addition to the
class-specific rows. Contents are deliberately **supplemental**: upstream
already grants the weapon, so the kit adds potions, return scrolls and the class
ammunition that upstream hands out inconsistently.

Item ids verified against `wz/String.wz/Consume.img.xml`:
`2000000` Red Potion, `2000003` Blue Potion, `2030000` Return Scroll,
`2060000` Arrow for Bow, `2070000` Subi Throwing-Stars, `2330000` Bullet.

Changing what fresh first jobs receive is therefore a pure data change.
Eligible advancement targets are exact IDs, not arithmetic job tiers: the five
Explorer first jobs, five Cygnus first jobs and Aran. Wind Archer and Night
Walker receive the same supplemental arrow/star policy as their Explorer
counterparts; Thunder Breaker receives no gun ammunition.

## Slice 4 — `@training`

Player command (rank 0), disabled through `coop.early_game.training_guide_enabled`.

```
@training          # spots for your current level
@training 25       # spots for a specific level
```

It only **reports**; it never teleports, so it cannot be used to skip travel or
content. Recommendations come from a lazy index built from the map WZ
(`coop/earlygame/TrainingSpots`): for every map, the dominant monster is
resolved and its level comes from the existing `LifeFactory.getMonsterLevel`, so
there is a single source of truth for mob level.

The index is built on first use and cached, so startup is not slowed down by a
feature nobody used. Qualification range is `coop.early_game.training_level_delta`
(default ±10), result count `training_max_results` (default 5).

## Slice 5 — Telemetry and analyzer

Cosmic's `server.ExpLogger` records gained EXP but no level, map, mob or job —
it cannot answer "how long do levels 1–30 actually take?".

Instead of widening the upstream schema, we add `coop_early_game_exp_log`
(migration `coop-1220`) and fill it from one guarded coop call site in
`Character.gainExpInternal`. It is:

- **opt-in** (`coop.early_game.telemetry_enabled`, default false);
- **asynchronous** (queue + batched insert, like `ExpLogger`), so a slow DB can
  never stall gameplay;
- **bounded and transactional**: queue and SQL batch sizes are clamped, flushes
  are serialized, and each batch explicitly commits or rolls back;
- **lifecycle-safe**: shutdown/restart stops periodic work and gives the final
  drain a bounded wait while the DB is still available;
- **fault-tolerant**: a balance query degrades to "no data" instead of throwing.

`coop/earlygame/TrainingAnalyzer` aggregates it per level (total EXP, samples,
EXP/hour derived from the observed wall-clock span).

**Known precision limits** (accepted for a balance tool; fix them only if the
numbers are ever used for anything load-bearing):

- `logged_at` is the **flush** time, not the moment the EXP was gained, so a
  sample carries up to `telemetry_flush_interval_seconds` (60 s) of jitter.
  EXP/hour is therefore an approximation, and it is unusable for a level that
  was finished inside a single flush interval.
- Only positive EXP accepted while the character's pre-award level is 1-30 is
  queued. The generic EXP pipeline cannot identify the origin truthfully, so
  these rows use source `UNATTRIBUTED` rather than claiming they came from mobs.
- A character deleted between queueing and flushing fails the foreign key. The
  batch is then split transactionally so only the invalid row is dropped and
  unrelated characters' samples still commit.

## Slice 6 — KPQ solo entry

`scripts/event/KerningPQ.js` required `minPlayers = 3`. It is now `1`, so the
main level 21–30 activity is enterable solo (D8 already relaxed expedition
minimums for the same reason).

**Lowering `minPlayers` alone is not sufficient**, and the first attempt got
this wrong. Stages 2–4 are "stand on the right spots" puzzles whose hardcoded
combinations (`stage2Combos`, `stage3Combos`, `stage4Combos` in
`scripts/npc/9020001.js`) require **exactly three** occupied spots. A solo runner
would therefore enter fine and then be permanently stuck at stage 2. Stage 1 had
the opposite problem: `numpasses = getPlayerCount() - 1` is `0` solo, and
`hasItem(id, 0)` is always true, so stage 1 would be free.

Both are fixed in `scripts/npc/9020001.js`:

- `combosForTeamSize(spotCount, teamSize)` generates the valid combinations for
  the current team size, so the number of required spots follows the party
  instead of being hardcoded to three.
- The required spot count is `max(0, playerCount - 1)`, matching upstream
  semantics: the leader stays at the NPC and does not occupy a spot. A solo
  runner therefore stays off every spot and confirms at Cloto; a full party
  still needs three.
- `rectangleStages` picks the combination and re-rolls a stale index when the
  team size changes (someone leaves mid-stage).
- Stage 1 keeps the quiz for solo runners. A solo entrant is always the event
  leader, so upstream sends them to the "collect N passes" branch — which demands
  a pass that only the quiz branch grants. Solo runners now answer the question,
  receive the pass and spend it themselves.
- The NPC instructions no longer say "3" but the current team size.

The two files must be kept in sync; `KerningPQ.js` carries a comment saying so.

## Configuration

All numbers live in the `coop:` block of `config.yaml`:

```yaml
early_game:
    beginner_sp_bonus: 3
    first_job_kits_enabled: true
    training_guide_enabled: true
    training_level_delta: 10
    training_max_results: 5
    telemetry_enabled: true  # current online playtest; Java default remains false
    telemetry_flush_interval_seconds: 60
    telemetry_queue_capacity: 100000
    telemetry_batch_size: 1000
    telemetry_shutdown_timeout_seconds: 5
```

Access is null-safe and clamped through `coop/config/CoopDefaults`.

## Integrity rules

- **No teleport.** `@training` only reports map ids and mob levels.
- **No free items bypassing validation.** Kits go through
  `InventoryManipulator.addById`, the same path a real pickup uses.
- **Kit cannot break advancement.** The grant is wrapped and logged; a missing
  table or a full inventory must never fail a job change.
- **Kit grant is guarded, not unconditional.** The kit is only granted when the
  *previous* job was a beginner job (Beginner/Noblesse/Legend), i.e. on a genuine
  beginner → first-job transition. A repeated GM `@job <firstjob>` therefore does
  not grant again. Note the precise limit: `@job <beginner>` followed by
  `@job <firstjob>` re-arms the transition, so a GM can still grant twice that
  way. This is GM-only (gm2) and accepted for now.
- **Items are never fabricated.** Kits go through
  `InventoryManipulator.addById`; a full inventory logs a warning and skips that
  item rather than duplicating or forcing it.
- **No runaway scaling.** Ultra flags affect beginner skills only; they are
  irrelevant from the second job onwards because the skills stop being used.

## Manual test checklist

1. Create a fresh Beginner → expect 3 SP available at level 1.
2. Spend the SP on Three Snails; kill a snail with shells in the inventory →
   damage is clearly multiplied (Ultra Three Snails).
3. Use Recovery → heal ticks roughly every 2 s, not 5 s.
4. Use Nimble Feet → large speed/jump increase.
5. Create a veteran character (if enabled) → **no** beginner SP bonus.
6. Advance a Beginner to Warrior at level 10 → kit granted: 50 Red Potions,
   50 Blue Potions, 5 Return Scrolls, plus the upstream weapon.
7. Advance to Bowman → additionally 2000 arrows; Thief → 1000 stars;
   Pirate → 2000 bullets. Wind Archer and Night Walker receive their configured
   ammunition; Thunder Breaker receives no bullets.
8. `@training` at level 15 → lists nearby maps with mob names/levels.
9. `@training 25` → lists level-25-range spots; confirm **no** teleport happens.
10. Set `training_guide_enabled: false` → command reports disabled.
11. Enter KPQ alone at level 21+ → instance starts solo.
12. **Clear all four KPQ stages solo.** This is the step that catches a
    half-finished solo change: stage 1 must still require a pass, and stages
    2–4 must clear while you remain off every puzzle spot instead of demanding
    three simultaneous occupants.
13. Die inside a solo KPQ run → the run ends (documented behaviour; see below).
14. With telemetry enabled, gain EXP at levels 1, 30 and 31, then wait for the
    flush → rows appear for pre-award levels 1 and 30 only, with level/map/job
    and source `UNATTRIBUTED`.
15. Run `@job <firstjob>` twice on one character → the kit is granted **once**.
16. Confirm no duplicate items, meso or EXP during any of the above.

### Known KPQ solo behaviour

With `minPlayers = 1`, `EventInstanceManager.isEventTeamLackingNow` returns
true as soon as the player count drops to `minPlayers`, so a solo run ends when
the player dies or disconnects. That is acceptable for now (a solo run is
restartable and costs nothing), but if solo KPQ becomes a real progression path
this should be revisited.
